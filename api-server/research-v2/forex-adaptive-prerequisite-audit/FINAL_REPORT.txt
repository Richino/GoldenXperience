================================================================================
1. OVERALL READINESS VERDICT
================================================================================

    PARTIALLY_READY  -  with one blocking data-integrity defect.

The *schema* is in unusually good shape. This repository already does the thing
most trading systems never do: it snapshots the strategy's own decision-time
evidence, immutably, per trade AND per rejected candidate, versioned against a
frozen configuration. Sections 2-7 below are largely a list of things that
already exist.

Three things stop this from being READY:

  (a) A LINKAGE DEFECT that is actively corrupting the adaptive engine's
      evidence today. 48 of the 55 executed multi-strategy trades are filed in
      paper_strategy_evaluations as never having executed. As a direct
      consequence, a *hypothetical* shadow outcome was computed for 48
      opportunities that were in fact traded for real, and
      loadAdaptiveEvidence() counts BOTH. ~24% of the observations the engine
      would learn from are duplicates of the same real opportunity.
      This is not a missing field. It is wrong data already in the tables.

  (b) SAMPLE SIZE. 55 multi-strategy trades over 3 calendar days
      (2026-08-19 -> 2026-08-21). The most populated exact evidence bucket
      (family x pair x session x regime x direction) holds 3 resolved
      observations. The engine's own thresholds are 50 (LEARNING) and 100
      (ACTIVE_SELECTION). Nothing is learnable at that volume - and the engine
      correctly refuses to act: 3,307 of 3,312 adaptive decisions are still
      in 'collecting'.

  (c) THE ORIGINAL-vs-INVERTED COMPARISON HAS ZERO ROWS. Both mechanisms exist
      and are correctly designed; neither has collected a single observation.

The correct move is to fix (a), keep collecting for (b), and stop treating (c)
as answered. Building an adaptive selector on the current tables would train it
on double-counted evidence over a 3-day sample.

================================================================================
4. EXACT FIELDS MISSING
================================================================================

  MISSING - ACTUAL FILL PRICE / SLIPPAGE
      There is no actual_entry, fill_price, or slippage column. `entry` is the
      INTENDED entry (the bid/ask read at decision time). When the trade reaches
      the broker, brokerCloseFor() reads state.averageClosePrice and derives
      result_r from the cash OANDA booked - so EXIT slippage is implicitly
      inside result_r, but ENTRY slippage is invisible and cannot be separated.
      50 of 84 trades have a submitted broker intent; 17 were rejected outright
      and 17 are still pending, so the ledger silently mixes broker-filled
      trades with paper-only ones and nothing distinguishes them on the row.

  MISSING - BID/ASK AT DECISION TIME ON THE TRADE ROW
      Only spread_pips is stored. The raw bid/ask exist on
      multistrategy_watch_snapshots, but that table is upserted per
      (instrument, family) and is overwritten every 60s - it is a live view, not
      an immutable snapshot. The quote a trade was built on is not recoverable.

  MISSING - ESTIMATED TRANSACTION COST IN R
      spread_pips is stored but never converted to a cost. Given that the
      documented 10,009-trade replay attributed the entire loss to the spread,
      spread_in_R (= spread_pips * pipSize / |entry - stop|) is the single most
      important derived field this ledger does not have.

  MISSING - NEWS CONTEXT ON REJECTED / SHADOW CANDIDATES
      All nine news_* columns live only on paper_strategy_trades. A shadow
      candidate cannot be sliced by news without recomputing the classifier
      against economic_calendar_events at query time. It IS derivable
      (evaluation.decision_time + instrument -> economic_calendar_events), but
      it is not stored, so shadow and executed rows are not directly comparable
      on the news dimension.

  MISSING - CALENDAR-COVERAGE FLAG ON THE TAG
      news_impact_tag = 'NO_NEWS' means "no matching event in the stored
      calendar", which for 22 of 84 trades means "no calendar data existed",
      not "no news". calendarCoverage() computes this on demand and the code
      comments call it out explicitly, but the row itself does not carry it.

  MISSING - VOLUME / LIQUIDITY / TICK DATA
      No volume is captured anywhere on the decision. Market structure is
      captured only as structureHighs/structureLows counts and the range fields
      inside MarketRegime (rangeHigh, rangeLow, rangeWidthAtr, rangeAgeBars).

  MISSING - SPREAD AND VOLATILITY IN THE ADAPTIVE EVIDENCE KEY
      loadAdaptiveEvidence() buckets on (family, pair, session, regime,
      direction) only. volatility_bucket, atr_pips, trend_strength,
      news_impact_tag and spread_pips are all STORED on the trade but are not
      dimensions the engine can learn over. This is a selector limitation, not
      a data gap - the columns are there.

  MISSING - A PAIRED ORIGINAL/INVERTED RECORD FOR EXECUTED TRADES (see section 8)

  MISSING - 'developing' / partial-setup progression
      setup_status supports 'developing' but the four Phase-2 strategies only
      ever emit valid / no_setup / invalid, so near-misses are indistinguishable
      from complete non-events.

8. ORIGINAL vs INVERTED MOMENTUM COVERAGE
================================================================================

STATUS: MISSING IN DATA. Two well-designed mechanisms, zero observations.

  paper_strategy_trades:  inverted = true              0 of 84
                          original_direction NOT NULL  0 of 84
                          inversion_experiment_id      0 of 84
  momentum_short_inversion_pairs:                      0 rows

WHY. experiment_activations records momentum-inversion-v1 activated at
2026-08-23T21:00:24Z. The last paper trade of ANY kind opened 2026-08-21. The
collector has run since (evaluations exist through 2026-08-24) but produced 0
valid candidates on 08-23 and 08-24 and 0 valid momentum SHORT candidates since
activation. The experiment is armed and has simply never fired.

CAN WE COMPARE original vs inverted TODAY?  NO - not for executed trades.

  applyMomentumInversion() is a REPLACEMENT policy, not a paired shadow. It
  rebuilds the trade on the opposite side of the book (correctly: it fills the
  other side at the real quote and pays its own spread rather than negating
  P&L, and it preserves stop/target DISTANCES so R:R is unchanged). But only one
  arm is ever executed. The original arm's geometry survives in the
  paper_strategy_evaluations row - written BEFORE inversion, so it holds the
  original entry/stop/target - yet resolveShadowCandidates() only labels rows
  with execution_status IN ('suppressed','blocked'), and the executing path
  promotes the row to 'selected'. So the original arm of an inverted trade will
  get no counterfactual outcome. Nothing else fills the gap.

  momentum_short_inversion_pairs IS the correct paired design - one row per
  opportunity holding both arms (orig SHORT at bid / inv LONG at ask, same
  distances mirrored), both shadow, plus horizon_returns at 1/3/6/12/24 bars,
  and an 'excluded' status with a reason so the denominator stays honest. It is
  deliberately excluded from the adaptive evidence loader so it cannot
  contaminate live selection. It is scoped to Momentum SHORT only and holds
  0 rows.

  The code's own frozen note is worth restating as an audit finding: the
  23-trade momentum sample of 2026-08-19->21 inverted from -7.19R to +7.13R, but
  an 11,977-signal historical replay put inverted momentum at -0.0600 vs
  original -0.0595 - i.e. no inversion effect at all. The two bodies of evidence
  disagree, and the sample that generated the hypothesis cannot confirm it.

CONCLUSION: shadow-trade records ARE needed for a paired comparison of executed
trades - and the right one already exists in table form. It needs (i) rows, and
(ii) extension beyond Momentum SHORT if the question is to be answered for the
Momentum family generally.

13. MINIMUM PREREQUISITE CHANGES
================================================================================

MUST HAVE - without these, adaptive learning would be unreliable
---------------------------------------------------------------

 M1. STOP DOUBLE-COUNTING EXECUTED OPPORTUNITIES IN THE EVIDENCE LOADER.
     Reason: 48 of 201 observations (24%) are the same real opportunity counted
     twice, once as an executed trade and once as a hypothetical. In 5 cases the
     two copies disagree on the outcome. Any expectancy the engine computes
     today is wrong by construction. Two parts: (a) exclude shadow rows whose
     evaluation matches an executed trade on (instrument, decision_time,
     family); (b) repair the 48 historical evaluation rows so paper_trade_id /
     trade_created / execution_status reflect what actually happened. The source
     fix for new rows is already in place - this is about the existing damage.

 M2. A CANONICAL "THIS OPPORTUNITY WAS EXECUTED" LINK THAT CANNOT DRIFT.
     Reason: M1 is only a repair. The link is currently maintained by an UPDATE
     that matches on three columns and has already failed silently once, for 87%
     of multi-strategy trades, for days, undetected. The trade row needs its own
     evaluation_id (or the evaluation needs a NOT NULL-when-executed guarantee),
     so "was this traded?" is a foreign key rather than an inference.

 M3. TRANSACTION COST IN R, ON THE ROW.
     Reason: spread_pips is stored but never expressed in the unit everything
     else is measured in. A prior 10,009-trade replay attributed the ENTIRE loss
     to the spread. A selector that ranks families by expectancy without cost
     will systematically prefer whichever family has the tightest stops - i.e.
     the highest cost per R. One derived column: spread_pips * pipSize /
     |entry - stop|.

 M4. MARK WHETHER A TRADE ACTUALLY REACHED THE BROKER.
     Reason: 50 submitted / 17 rejected / 17 pending. Broker-filled trades are
     scored from OANDA's realizedPL (carrying exit slippage); the rest from
     candles at exact levels. Pooling two measurement regimes in one result_r
     column means the engine learns a blend of a real cost structure and an
     idealised one. A single execution_source column resolves it.

 M5. ROWS FOR THE ORIGINAL-vs-INVERTED COMPARISON.
     Reason: this is the one strategy question the system is explicitly built to
     answer, the tables exist, and both hold zero rows. Not a schema change -
     the momentum_short_inversion_pairs design is correct. It needs the
     experiment to actually fire, and its scope widened past Momentum SHORT if
     the question is about the Momentum family. Until then, treat "invert
     momentum" as untested.


SHOULD HAVE - would materially improve learning
-----------------------------------------------

 S1. CALENDAR-COVERAGE FLAG ALONGSIDE news_impact_tag.
     Reason: 22 of 84 NO_NEWS tags mean "no calendar existed". Without a flag on
     the row, any news cut silently mixes "no news" with "no data" and will
     understate the news effect. calendarCoverage() already computes it.

 S2. FIX OR RETIRE news_status.
     Reason: it reads 'not_evaluated' on all 55 multi-strategy trades even
     though the news gate ran and passed on all 55. A column that contradicts
     the conditions[] array on the same row is worse than no column.

 S3. NEWS CONTEXT ON EVALUATIONS/SHADOW CANDIDATES.
     Reason: 146 shadow observations already outnumber the 55 executed ones and
     will keep doing so. Excluding them from every news cut throws away the
     majority of the evidence. 13,248 evaluations fall inside the calendar span.

 S4. EXTEND THE EVIDENCE KEY BEYOND (family, pair, session, regime, direction).
     Reason: volatility_bucket, atr_pips and trend_strength are stored on every
     trade and are the most plausible explanations of why a family fails, but
     the engine cannot express them. Note the tension: the ladder already needs
     50-100 observations per bucket and the deepest bucket has 3, so extra
     dimensions must be added as ADDITIONAL rungs, never as a finer exact key.

 S5. BID/ASK AT DECISION TIME ON THE TRADE ROW.
     Reason: only spread_pips survives. The quote itself lives on
     multistrategy_watch_snapshots, which is overwritten every 60 seconds, so
     the price a trade was built on is unrecoverable after the fact - which
     blocks any later re-pricing or execution-quality analysis.


NICE TO HAVE - useful later, not worth delaying the first adaptive version
-------------------------------------------------------------------------

 N1. Actual fill price / entry slippage from the broker fill transaction.
     Reason: exit slippage is already implicit in broker-derived result_r; entry
     slippage is the remaining unknown. Only meaningful once broker-filled
     trades are separable (M4) and numerous.

 N2. Candle volume on the decision snapshot.
     Reason: the only requested context genuinely absent everywhere. Cheap to
     add, but no current strategy reads it, so nothing would consume it yet.

 N3. Emit 'developing' from the four Phase-2 strategies.
     Reason: setup_status supports it; the strategies never use it, so a
     one-gate near-miss is indistinguishable from a flat non-event among 13,101
     no_setup rows. Would sharpen threshold-sensitivity analysis.

 N4. Drop the dead scaffolding (evaluation_features, trade_candidates,
     outcome_labels, paper_trades, paper_trade_events - all 0 live rows).
     Reason: hygiene only. They invite a future reader to join the wrong table.

DELIBERATELY NOT RECOMMENDED
     No new indicators. Every field above is justified by a specific question
     the current data cannot answer. Adding RSI/MACD/Bollinger/etc. "in case
     they help" would grow the snapshot without growing what can be learned from
     55 trades, and the four strategies already persist exactly the inputs their
     own gates read.

14. RECOMMENDED ARCHITECTURE FOR THE FUTURE ADAPTIVE ENGINE
================================================================================

The architecture in the brief already exists in this repository. Do not rebuild
it. The mapping is one-to-one:

    Market opportunity      ->  getMultiStrategySnapshot() + computeRegime()
    Strategy evaluation     ->  4 pure Strategy.evaluate() implementations
    Decision-time snapshot  ->  features jsonb + conditions jsonb + regime columns
                                + config_version -> immutable strategy_configs
    Trade / rejection       ->  paper_strategy_trades / paper_strategy_evaluations
                                (+ adaptive_decisions as the decision audit trail)
    Outcome                 ->  resolveOpenTrades / fastResolve / liveResolve
                                + shadow_candidate_outcomes for the counterfactuals
    Statistical memory      ->  loadAdaptiveEvidence() -> EvidenceStore
    Adaptive selector       ->  decideInstrument() - pure, 3-state, unit-tested
    Future decision         ->  the next collector tick

The design decisions already made here are the right ones and should be
preserved rather than re-litigated:

  - The selector is PURE and separated from I/O. decideInstrument() takes
    candidates + evidence and returns a decision; only loading and logging touch
    the database. This is what makes it testable and replayable.
  - Configurations are IMMUTABLE AT THE DATABASE, enforced by a trigger, not by
    convention. A parameter change is a new config_version. Every historical
    trade is reproducible.
  - Evidence is keyed PER CONTEXT with a ladder from exact to aggregate, and the
    state machine's thresholds are counted per bucket, never globally. 100
    trades spread across unrelated pairs cannot unlock active selection for one
    context. Keep this.
  - Suppression requires BOTH a sample-size threshold AND a one-sided
    negative-expectancy confidence test. Sample count alone is never enough.
  - Non-executed candidates are preserved and their counterfactual outcomes
    resolved with the SAME labelOutcome() the real trades use. This is the
    defence against selection bias and it is already working (146/146 resolved).
  - Research tables are deliberately excluded from the evidence loader
    (momentum_short_inversion_pairs) so a frozen hypothesis cannot leak into
    live selection.
  - Evidence is keyed on COALESCE(original_direction, direction) so an inverted
    trade lands in the bucket the strategy will consult next time. Correct, and
    it will matter the moment inversion produces its first row.

The only architectural CHANGES worth making are the ones section 13 lists - and
note that M1/M2 are corrections to how the existing pieces connect, not new
pieces. The single structural weakness is that "was this candidate executed?" is
maintained by a multi-column UPDATE rather than a foreign key, and that is
exactly where the system has already failed silently once, at 87% failure rate,
undetected for days.

One sequencing observation: the engine cannot leave 'collecting' for any context
until buckets reach 50 observations. At the current rate - 55 executed + 146
shadow over 3 trading days, spread across 4 families x 12 pairs x 3 sessions x 3
regimes x 2 directions - the exact buckets will not fill for a very long time.
The ladder's coarser rungs will fill first, which is the intended behaviour, but
it means the practical near-term value of this data is OFFLINE RESEARCH over
paper_strategy_evaluations + shadow_candidate_outcomes, not online adaptation.


================================================================================
FINAL RECOMMENDATION
================================================================================

                        FIX DATA COLLECTION FIRST

Specifically: fix the trade/evaluation linkage and the resulting double-count
(M1, M2). That is a genuine defect writing wrong evidence into the only tables
the adaptive engine reads - 24% of its observations are duplicates today, and in
5 cases the duplicate disagrees with the truth. It is not a missing feature and
it will not fix itself by collecting more data; it will scale.

Then add the three cheap columns that make the existing data interpretable
(M3 cost-in-R, M4 broker-vs-paper, S1 calendar coverage) and correct the one
column that is actively misleading (S2 news_status).

After that: CONTINUE COLLECTING WITHOUT ACTIVE ADAPTATION. The instrumentation
is genuinely good - better than most systems ever get - but 55 trades over 3
days, one family that has never traded, and a 3-observation deepest bucket
cannot support a selector. The engine's own state machine already knows this and
is refusing to act, which is the correct behaviour and should not be overridden.

DO NOT BUILD THE ADAPTIVE ENGINE YET. Not because the plumbing is missing - it
is almost entirely there - but because what it would learn from today's tables
is 24% duplicated, 3 days long, and blind to the cost that a 10,009-trade replay
already identified as the whole loss.
